# Architecture and implementation contracts

## Repository layout to create

This is a suggested organization, not a reason to create empty abstractions for unused capabilities. Keep interfaces small and add files when implemented.

## Environment contract
```javascript
// Contract sketch; use concrete JSDoc types in implementation.
env.reset({ seed });
// -> { state, observation, info }
env.step(action);
// -> { state, observation, reward, terminated, truncated, info }
env.getState();
env.getObservation();
env.serialize();
env.getModel(); // granted only to planning/reference code
```

State must include the features that affect transitions/reward: position, inventory bits for consumed collectibles, battery when used, weather phase when used, and remaining time for finite-horizon tasks. A plain position-only state is correct for early static maps with no additional dynamic variables. Use an explicit `StateEncoder` to build tabular keys and neural features.

Keep observation separate from privileged simulation state. A restricted observation is an explicit lesson design. Model-free agents receive observations and transition samples, not the ground-truth transition function. The renderer can read privileged state for teaching when the view is clearly labeled.

Actions initially use a stable order: up, right, down, left. Boundary/wall collisions remain in place under a specified reward rule. A terminal state produces no repeated terminal rewards. Define whether a goal reward includes or replaces step cost and test that choice. Verify transition probabilities sum to one, including merged wall/boundary outcomes.

Expose one canonical pure transition/reward implementation to both the sampled environment and the exact planning model so they cannot silently diverge. Store a scenario hash/version with every run.

## Agent contracts

Do not force prediction methods and control methods to pretend to be the same algorithm. Use capabilities such as `requiresModel`, `supportsTraining`, `supportsPrediction`, `supportsPolicy`, `supportsValues`, `supportsQ`, `supportsBatch`, and `supportsTransfer`.

A control agent supports action selection, transition/episode observation, a frozen evaluation snapshot, serialization, and diagnostic snapshots. A prediction learner consumes experience generated by a separate policy. A planner performs sweeps/backups using an explicitly supplied model. The lesson UI enables only compatible operations.

The action explanation records selection-time values, action probabilities, behavior/target policy identity, epsilon, random branch/draw when relevant, action selected, and tie rule. The update explanation records pre-update values, target terms, terminal/truncation flags, update delta, and post-update values. The UI formats these records; it does not recalculate them with a second implementation or use an LLM.

## Training coordinator and worker protocol

Exactly one training coordinator owns the active environment/agent pair. Modes: idle, manual, stepping, training, evaluating, replaying. Invalid concurrent actions are disabled with an explanation. A route change either pauses/cancels or explicitly keeps the run alive; it never spawns a second hidden trainer.

Worker requests include `runId`, `commandId`, protocol version, immutable configuration hash, and command payload. Commands: initialize, step, episode, train, pause, resume, cancel, evaluate, snapshot, dispose. Responses: ready, progress, stepTrace, checkpoint, paused, completed, cancelled, error. Acknowledge commands and ignore stale messages from old run IDs.

Use chunked execution with yields inside the worker, not a single uninterruptible million-step loop. Batch progress at up to ten updates per second initially. Return bounded sampled trajectories and aggregate metrics, not every transition forever. Rendering uses requestAnimationFrame on the main thread; changing rendering speed cannot alter RNG consumption or learned results. [S7]

A mid-run parameter/environment change creates a new experiment version or waits until the current run finishes. An explicitly taught nonstationary experiment logs its change point and is labeled as such.

## Determinism and checkpoints

Use a documented seeded PRNG with separate streams for environment transitions, action exploration, replay sampling, and network initialization. Derive episode seeds reproducibly. Do not use Math.random in scientific core code. Rendering gets a separate decorative RNG or no randomness.

Tabular CPU runs should replay exactly under identical configuration. Neural runs record backend/device/library versions and compare with tolerances; do not promise bitwise identity across GPU hardware. Checkpoints include state/action schema, scenario hash, algorithm version, weights/table, optimizer state when exact resumption is supported, RNG states, and counters. A weights-only export must be labeled inference/initialization, not exact continuation.

## Evaluation contract

Freeze the learned policy and turn off learning updates. Specify greedy, stochastic-policy, or another named evaluation rule. Use fresh evaluation seed suites and store them. Report success, task return, discounted return when needed, episode length, failure rate, environment interactions, gradient/planning updates, and elapsed time with definitions.

Separate raw episode results from plot smoothing. Report the count of independent trained agents and evaluation episodes per agent. Prefer intervals computed over independent agent-level summaries for training variability; do not treat all episodes from one trained model as independent training replicates.

For Dyna-Q, simulated planning updates are not free environment interactions and must not be counted as real samples. In comparisons, show both sample budget and computational work. Different methods can consume the same random seed list without following identical trajectories.

## Persistence and imports

Use a namespaced localStorage key, such as `rl-island:progress:v1`, for small settings/progress and a namespaced IndexedDB database for experiments and models. [S8-S9] Catch unavailable storage, quota failures, migrations, and private-browsing limitations; provide a memory-only mode and export option instead of crashing.

`ProgressRecord`: schema version, curriculum version, lesson states, check answers, completion timestamps, preferences, current route. `ExperimentRecord`: run ID, immutable scenario/representation/configuration, seeds, software version, train/evaluation separation, metrics, optional checkpoint link, reflections. `ExportEnvelope`: format name, schema version, creation time, payload kind, bounded payload, integrity digest for accidental-corruption detection only.

Validate supported keys/types/ranges before allocation. Reject oversized maps/tensors, NaN/Infinity, incompatible action orders, and executable content. Do not merge prototype-related keys into objects. Render notes using textContent. A digest is not a signature and does not authenticate a grade. Never import arbitrary remote code, model URLs, or notebook HTML.

## Suggested bounds to benchmark

Early maps: 8x8 to 12x12. Editor maximum initially 40x40. Tabular encoders warn before 50,000 reachable/state-key combinations. Default replay capacity around 5,000 transitions with a configurable upper cap. DQN starts with vector observations and two small hidden layers, for example 32 units each. These are initial engineering choices, not empirically validated speed claims.

## Hosting and offline behavior

Build an isolated static sub-application. Hash routing avoids reliance on host rewrite rules. Configure Vite base for the approved path. Cache locally bundled assets after first load and expose explicit offline readiness. Service-worker scope and cache names stay under the app; never take control of the whole ACML origin. Updates must not delete student IndexedDB records. Do not silently refresh the page while a training run or unsaved notebook edit is active. [S6, S13]
